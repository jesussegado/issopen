# Phase 01 — UI Design Contract

> Visual and interaction contract for the private single-owner dogfooding MVP. Generated by gsd-ui-researcher and approved by gsd-ui-checker.

---

## Contract Scope

Phase 1 ships one quiet, functional, authenticated English-language web product. It must let the owner create a personal workspace, create projects and issues, work a five-state board, inspect server-attributed activity, connect ChatGPT, govern a separately authenticated Codex identity, and review a returned code result. The interface is responsive HTML in a normal browser; no desktop wrapper is permitted.

The UI must make this loop obvious:

```text
create and prioritize an issue
  -> ChatGPT inspects or updates it through OAuth MCP
  -> Codex claims it with a separate scoped PAT
  -> Codex links a branch, commit, or pull request
  -> Codex moves it to Ready for Review
  -> the owner accepts the result or requests changes
```

Issopen records the work and review. It must never imply that it edits the repository, runs CI, merges, or deploys.

### Explicit Phase Exclusions

- No public registration, invitations, collaborators, comments, mentions, or notifications.
- No labels, search, filters, archive/restore, saved views, bulk actions, or customizable workflows.
- No attachments, screenshots, Chromium extension, audits, quotas, billing, or Cloud UI.
- No drag-and-drop requirement. Do not install `dnd-kit` in this phase.
- No native or packaged desktop/mobile app.
- No dark theme, theme switcher, localization framework, marketing site, illustrations, dashboards, charts, or gamification.
- No project deletion or issue deletion. The only destructive UI action in this phase is agent-credential revocation.

## Design System

No design system or component library exists in the greenfield codebase. The owner declined shadcn on 2026-08-31. Build a minimal phase-local component set from semantic HTML, native controls, React, and Tailwind CSS tokens. Do not initialize shadcn, add `components.json`, select Radix/Base UI, or create a shared `packages/ui` package.

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none |
| Styling | Phase-local Tailwind CSS 4 tokens; exact package version must be revalidated with the implementation cohort |
| Icon library | none; use a tiny local inline-SVG set only for menu, close, chevron, copy, external-link, user, bot, and system symbols |
| Font | `system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif`; `ui-monospace` only for issue keys, repository values, URLs, and the one-time PAT |
| Locale | English only for Phase 1 |
| Theme | Light only for Phase 1 |

### Visual Character

- Functional, compact, and calm: a small engineering tracker, not an analytics dashboard.
- After a project is selected, its board is the primary visual anchor: it receives the widest content area, and `Create issue` is its single dominant accent action.
- Use borders and surface contrast to establish hierarchy. Cards have no default shadow.
- Use the approved six-piece aperture icon with the `Issopen` wordmark through the shared `Brand` component. The 2026-09-07 owner decision supersedes the original text-only identity; see [design decision 0001](../../../docs/design/0001-brand-identity.md).
- Default radius is `8px`; large page panels use `12px`; pills use a full radius.
- Borders are `1px`. Focus rings are `2px` with a `2px` offset.
- Motion is limited to opacity or color transitions of `120ms`; honor `prefers-reduced-motion` by removing transitions.

### Phase-Local Primitive Inventory

Implement only these reusable primitives inside the web application. Screen-specific composites remain beside their routes.

| Primitive | Contract |
|-----------|----------|
| `Button` | Native `<button>`; variants `primary`, `secondary`, `ghost`, `destructive`; visible text is required except the mobile menu and close controls, which require `aria-label`. |
| `Field` | Persistent `<label>`, native input/textarea/select, helper text, inline error, and `aria-describedby`; placeholders never replace labels. |
| `TextInput` / `TextArea` | Native controls; preserve entered values after validation or network errors; no rich-text editor. |
| `Select` | Native `<select>` for status, priority, code-link type, expiry, and mobile status filtering; do not implement a custom listbox. |
| `Link` | Native anchor with visible focus. External code links include an external-link symbol, accessible “opens in a new tab” text, and `rel="noopener noreferrer"`. |
| `Badge` | Text-first neutral pill for issue key, priority, actor type, agent claim, source, and credential status; never communicates meaning by color alone. |
| `StatusBanner` | Inline page-level feedback with `role="status"` for success/progress or `role="alert"` for errors; no toast dependency. |
| `ConfirmationPanel` | Inline two-step confirmation with heading, consequence text, a contextual secondary action that names the safe outcome, and the explicit primary/destructive action; generic dismiss labels are prohibited. No custom modal. |
| `SecretRevealPanel` | One-time PAT output in monospace with `Copy token`, manual-selection fallback, and `Finish agent setup`; never persisted in client storage after the response is dismissed. |
| `Skeleton` | Shape-matched loading placeholder marked `aria-hidden="true"`, paired with one screen-reader status message. |
| `MobileNavigation` | Inline expandable navigation below the header using `aria-expanded`; Escape closes it and focus returns to its trigger. No overlay or focus-trap dependency. |

## Spacing Scale

Declared values are multiples of four and are the only spacing values allowed:

| Token | Value | Usage |
|-------|-------|-------|
| `xs` | 4px | Icon gaps, compact inline separation |
| `sm` | 8px | Related labels, metadata, compact controls |
| `md` | 16px | Default card padding, control groups, board gaps |
| `lg` | 24px | Section padding, page-header separation |
| `xl` | 32px | Major layout gaps and form sections |
| `2xl` | 48px | Empty states and page-level separation |
| `3xl` | 64px | Desktop page breathing room only |

Exceptions: none. Component dimensions are also multiples of four except the intentional `44px` minimum touch target, itself a multiple of four.

### Fixed Component Dimensions

- Desktop header: `64px`; mobile header: `56px`.
- Desktop sidebar: `240px`.
- Form controls and buttons: `40px` minimum height with a fine pointer; `44px` with a coarse pointer or below `768px`.
- Board column: `280px` minimum and `360px` maximum.
- Reading/form column: `720px` maximum.
- Issue-detail layout: `1200px` maximum.

## Responsive Layout

| Viewport | Contract |
|----------|----------|
| `320–767px` | One-column app. Header uses expandable inline navigation. Forms and issue detail fill the width with `16px` page padding. The board defaults to grouped vertical lists and offers a native `Show status` select with `All statuses` plus the five fixed states. |
| `768–1023px` | Header navigation remains compact. The board is a horizontally scrollable region of `280px` columns with visible keyboard-focusable overflow controls; page content itself must not horizontally scroll. |
| `>=1024px` | Persistent `240px` sidebar and main content. Board columns use the remaining width and scroll within the board region only when five columns do not fit. Issue detail becomes a content/activity two-column layout. |

### App Shell

- Header: approved icon with Issopen wordmark, current workspace name, owner menu with `Workspace settings` and `Sign out`. At `420px` and below, the authenticated header shows the icon alone while retaining the accessible `Issopen home` link name.
- Desktop sidebar: project links, `Create project`, `Agents`, and `Connect ChatGPT`. The current route uses dark accent text, a mint background, a forest marker, and `aria-current="page"`.
- Main content starts with a page title, one-sentence context when needed, and no more than one primary CTA.
- The selected project's board is the authenticated product's primary visual anchor. `Create issue` is the only dominant accent action in its header; project settings and navigation remain secondary.
- Provide a visible-on-focus `Skip to main content` link.
- Forms use dedicated routes rather than dialogs or side sheets.

### Board Composition

- Desktop/tablet: five semantic sections in this exact order: `Backlog`, `Ready`, `In Progress`, `Ready for Review`, `Done`.
- Mobile: the same order as grouped sections. `Show status` can reduce the view to one section without changing issue state.
- Each section has a heading and count. Its cards are an HTML list.
- The board is not a table and does not require drag-and-drop.

## Information Architecture and Screen Contracts

### 1. Minimal Status Page

- A data-free `/status` surface may be anonymous because it exposes no tracker content.
- Ready state: `Issopen is ready` and a `Sign in` link.
- Starting state: `Issopen is starting` and `Try again`.
- Do not show database hosts, workspace existence, owner email, configured domains, tokens, stack traces, or secrets.

### 2. Owner Sign-In and Recovery

Phase 1 interaction default under D-09 discretion:

- The operator creates the only owner through the documented bootstrap command before tracker access is possible. There is no anonymous browser owner-creation route.
- Web sign-in uses the owner email and password established during bootstrap.
- Heading: `Sign in to Issopen`. Supporting copy: `This is a private Issopen instance.`
- Recovery remains an explicit operator command and invalidates active owner sessions. The sign-in helper says `Lost access? Use the documented owner recovery procedure.` Do not invent a command name in the UI.
- Invalid credentials use the exact privacy-safe error `We couldn't sign you in. Check your email and password, then try again.` The recovery action is `Try signing in again`, which retains the email, clears the password, and returns focus to the password field. The copy and behavior reveal neither whether the owner exists nor whether the instance has been bootstrapped.

### 3. First Authenticated Entry

- Route the first successful owner session to `Name your workspace`.
- Show one required `Workspace name` field, prefilled with `My workspace`, and primary action `Create workspace`.
- On success, route to the no-project state. This is not the deferred multi-step onboarding checklist.
- Workspace settings later exposes the same name field and `Save workspace` action.

### 4. Project Creation and Settings

- No-project heading: `No projects yet`.
- Body: `Create a project to start a private backlog.`
- Primary action: `Create project`.
- Creation fields, in order: `Project name`, `Project key`, `Description`, then optional `Repository URL`, `Default branch`, and `Repository subdirectory` under a `Repository context` heading.
- Project key is suggested from the name, shown in uppercase, and remains a server-validated stable project value. Editing project data must never rewrite existing issue keys.
- Repository fields are plain data. Issopen never requests Git credentials, clones the repository, fetches link previews, or claims repository access.
- Project settings exposes the same fields with `Save project`; no archive or delete action appears in Phase 1.

### 5. Project Board

- Header shows project name, stable key, optional repository host/path, `Project settings`, and primary `Create issue`.
- A project with no issues uses `No issues yet` and `Create the first issue to start this project's backlog.`
- Each `IssueCard` shows stable issue key, priority text, linked title, `Owner: You`, and `Agent: {name}` only when claimed.
- Each card contains a native status select whose accessible name is `Change status for {issue key}`. It lists the five locked states exactly.
- The server response is authoritative. While saving, disable only that issue's status select and show `Saving…`. Move the card only after the mutation and activity event are accepted.
- After a successful move, retain focus on the moved issue's status select and announce `{issue key} moved to {status}` in the page live region.
- An empty column says `No issues` without repeating a CTA.

### 6. Create and Edit Issue

- Use dedicated full-page forms.
- Fields, in order: read-only project, required `Title`, optional multiline `Description`, `Priority`, and `Status`.
- Priority is one shared four-value enum: `Low`, `Medium`, `High`, `Urgent`; default `Medium`. Render text, never color alone.
- Description is plain text in Phase 1. Preserve line breaks, escape HTML, and provide no rich-text or Markdown toolbar.
- Create action: `Create issue`. Edit action: `Save issue`.
- On success, the owner lands on the stable issue-detail route and sees `Issue created` or `Issue updated`.
- On failure, keep all input and place the error before the first invalid field or in the page banner for a server/network error.

### 7. Issue Detail and Human Review

- Header shows issue key, title, priority, status control, `Owner: You`, and separate agent claim state.
- Main content order: description, repository context, code results, review panel when applicable, then edit action.
- Desktop activity occupies the right column; mobile activity follows the issue content.
- `Code results` lists branch, commit, and pull-request URLs by explicit type. Owner-added links use an inline native form with `Link type`, `URL`, and `Add code link`.
- Never fetch, embed, or preview a repository/result URL. Opening it is an explicit external navigation.
- When the issue is `Ready for Review`, show a `Review result` panel with the linked code results and two owner-only actions:
  - `Accept result` moves the issue to `Done` and records an owner review-accepted activity event.
  - `Request changes` reveals a required `Reason` textarea; confirmation moves the issue to `In Progress` and records the reason in a review-requested-changes activity event.
- Neither action implies merge, deployment, CI success, or repository verification.
- If `Ready for Review` has no code result link, show `No code result is linked yet.` The UI warns but does not fabricate or preview evidence.

### 8. Activity Chronology

- Render an ordered vertical list with one item per server event.
- Each item shows actor type and concrete identity, source, absolute timestamp, and bounded change summary.
- Human: `You` with user symbol. Agent: `Agent · Codex` or the actual agent name with bot symbol. System: `System` with system symbol.
- Sources are explicit text such as `Web`, `MCP`, or `System`.
- Use an unambiguous timestamp such as `31 Aug 2026, 14:32`; relative time may be secondary but never replaces it.
- Activity is immutable and has no edit, delete, or client-supplied actor/time controls.
- Creation, field/status changes, claims/releases, code links, and review outcomes must have distinct human-readable summaries.

### 9. Agent Access

- Heading: `Agents`. Empty state: `No agents yet` / `Create a separate identity before giving a code agent access.`
- Agent rows show name, description, allowed projects, granted scopes, credential status, expiry, and `Last used` (`Never` when absent). Revoked identities remain visible for attribution.
- `Create agent` opens a dedicated form with name, description, required project allowlist, explicit scopes, and expiry.
- Scope labels are: `Read issues`, `Claim or release work`, `Edit issue fields`, `Link code results`, `Move work through Ready for Review`, and `Close issues`.
- Default grant for Codex checks the first five scopes and leaves `Close issues` unchecked. The close scope appears last with helper copy `Allows this agent to move issues to Done. Human review remains the default.`
- Expiry defaults to `30 days`; the owner may choose another offered finite duration or `No expiry` explicitly.
- After creation, replace the form with the one-time `SecretRevealPanel`: `Copy this token now. You won't be able to see it again.` Show `Copy token`, a manual-selection fallback, and `Finish agent setup`.
- Never place the PAT in a URL, browser storage, analytics, later API responses, or logs.
- `Revoke credential` first opens the inline confirmation panel: `Revoke agent credential? {agent name} will lose access immediately. Existing activity will remain. This can't be undone.` Actions are `Keep agent access` and `Revoke credential`.

### 10. Connect ChatGPT and OAuth Consent

- Authenticated navigation label: `Connect ChatGPT`.
- Page heading: `Connect ChatGPT to Issopen`.
- Show the configured HTTPS MCP URL as read-only monospace data with `Copy MCP URL`.
- Present four numbered steps: copy the URL; add it as a personal MCP plugin in ChatGPT Work; authorize access in Issopen; ask ChatGPT to list the private projects.
- Do not claim `Connected` merely because the URL was copied. A connected state requires a successful server-observed OAuth authorization or tool request.
- OAuth consent is a dedicated page. If the owner has no session, sign in and return to consent afterward.
- Consent heading: `{client name} wants to access Issopen`. Render the client name and requested scope descriptions as escaped plain text.
- Show the private workspace name and exact requested read/write capabilities. Actions are `Allow access` and `Deny access`.
- Tokens, authorization codes, PKCE values, PATs, and client secrets are never rendered.
- OAuth failure copy: `We couldn't authorize ChatGPT. Return to ChatGPT and try connecting again.`

## Interaction and State Contract

### Forms and Mutations

- No autosave. The owner submits explicit create/save/review actions.
- Disable the submitting action, change its text to a present participle such as `Creating…` or `Saving…`, and prevent duplicate submission.
- Validate on submit and on blur after the first submit. Move focus to the error summary, link each summary item to its field, and retain all entered values.
- Successful mutations show an inline `StatusBanner` at the top of the affected page and update only from the authoritative server response.
- Network failure copy: `We couldn't save your changes. Check your connection and try again.`
- An expired owner session redirects to sign-in without rendering protected data; after sign-in, return to the intended in-scope page.
- Missing and unauthorized protected resources share the privacy-safe heading `This page isn't available.` and body `The link may be invalid, or you may not have access. Return to your projects and try again from there.` The recovery action is `Return to projects`; the UI does not confirm whether the resource exists.

### Loading, Empty, and Error States

- Initial route loading uses shape-matched skeletons; background refresh keeps current content and labels the affected control `Updating…`.
- Never show a blank board, empty panel, raw JSON, stack trace, or indefinite spinner.
- Empty states describe what is absent and provide one next action.
- Inline errors remain until the next attempt succeeds or the owner dismisses them.
- If the browser goes offline, show `You're offline. Changes can't be saved until you reconnect.` and disable mutation actions while preserving readable content.

### Keyboard and Focus

- Every flow—sign-in, workspace/project/issue creation, board status movement, issue review, ChatGPT consent, agent creation, token copy, and revocation—must complete with keyboard only.
- Native status selects are the canonical board movement control. Drag-and-drop must not be added as the only or primary path.
- Focus order follows visual order. Focus is never placed on static cards or wrapper elements.
- Route changes focus the page `h1`; save responses focus the banner only for errors, not ordinary success.
- Expandable mobile navigation closes on Escape and returns focus to its trigger.
- New content and board moves are announced through one polite live region; errors use an assertive region.

### Touch and Pointer

- Interactive targets are at least `44px` square on coarse pointers and mobile viewports.
- Do not require hover to discover a control or full text.
- Links, buttons, and selects retain visible focus and pressed/selected states independent of hover.

## Accessibility Contract

- Target WCAG 2.2 AA contrast and interaction behavior for every Phase 1 surface, even though the product-wide audit requirement lands later.
- Use one `h1` per route, sequential headings, and semantic `header`, `nav`, `main`, `section`, `form`, `ol`, and `ul` elements.
- Every form control has a visible label. Required state and errors are conveyed in text and programmatically.
- Board columns are labeled sections; issue cards are list items; the issue title is the navigation link.
- Status, priority, actor type, claim state, credential state, and review outcome are never color-only.
- Inline SVGs are `aria-hidden="true"` when adjacent text names the action; icon-only controls have explicit accessible names.
- Text remains readable and functionality remains available at 200% zoom and at a `320px` viewport without two-dimensional page scrolling.
- External links identify that they open a new tab. PAT copy success is announced without reading the secret aloud.
- Playwright acceptance must cover keyboard-only status movement, focus retention after a card moves, project/issue forms, review actions, OAuth consent, one-time PAT handling, and credential revocation.
