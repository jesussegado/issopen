# Ticket 126 — Invariantes transaccionales del tracker

## Objetivo

Dar una sola implementación a los invariantes repetidos de mutación del
tracker sin ocultar las transacciones ni convertir Drizzle en un repositorio
genérico.

## Trabajo

1. Ejecutar primero las caracterizaciones de carreras CAS e instantáneas de
   preguntas.
2. Reforzar la prueba concurrente para verificar que sólo la mutación ganadora
   genera auditoría con actor, origen, resumen y cambios.
3. Extraer helpers con intención de dominio para bloqueo de tickets activos,
   versión esperada, decisiones de preguntas, sello de mutación y actividad.
4. Sustituir la duplicación conservando explícitos los filtros adicionales,
   las consultas de negocio y el caso idempotente especial del borrado.
5. Ejecutar tracker, HTTP, MCP y todos los gates; desplegar por imagen inmutable
   y comprobar Argo, pod, HTTP y PVC.

## Riesgos y rollback

- Riesgo: perder el filtro de workspace o aceptar tombstones en una mutación.
- Control: el predicado compartido siempre incluye workspace, id y `deletedAt`
  nulo; el borrado conserva deliberadamente su consulta separada con tombstone.
- Riesgo: cambiar mensajes o semántica de conflicto.
- Control: cada call site conserva su mensaje y las suites REST/MCP completas.
- Rollback: revertir el commit de código; no hay migración ni cambio de contrato.
